# 旧口径结果（`feature_version = fullcycle-v1`，已作废）

这里的 172 个 JSON 是 **M1–M4 的原始结果**，由错误的特征口径训出。保留它们
只为一件事：让「特征修复到底改了多少」这个问题可以被逐 run 核对，而不是靠
回忆。

## 为什么作废

`matr.charge_curve()` 返回的是**整条循环**（充电段 + 放电段），而
`features.delta_q_curve()` 会按电压 `argsort` 再插值。于是放电段（其 `Qc`
通道恒定）被打散进充电段的电压区间，低电压区出现一片「容量 = 满容量」的
平台。

b1c0 循环 1 的实测：

| 口径 | ΔQ 总变差 | std | 与正确值的相关系数 |
|---|---|---|---|
| `fullcycle-v1`（本目录） | 269.60 | 0.3918 | **−0.019** |
| `discharge-v2`（现行） | 0.21 | 0.0026 | 1（定义） |

全量 2700 行的 TV/幅度 中位数从 **122.4** 降到 **5.9**。

**最要命的地方是它不报错**：形状对、长度对、不抛异常，而且 C0 照样训出
MAE 0.0016 的模型——看起来是个好结果。只有总变差能指出它。

详见 `docs/plan.md` §13.5.2 与 §14 坑 26。

## 这些数字能用来做什么

- **可以**：与 `results/` 里的新结果做**同设置**配对对比。正确的做法是
  用 `scripts/rerun_all.py --features data/mit-stanford/features.fullcycle-bug.parquet`
  在同一线程数下重跑一遍，而不是直接拿本目录的数字和新数字相减——见下一条。
- **不可以**：直接当作实验结果引用，或与 `results/` 的数字直接相减。

## 相减之前必须知道的两件事

这两条都不是"精度噪声"，而是会改变数值的实验设置，而且**从数字上看不出来**：

1. **线程数**。本目录的数字跑在默认线程数（24）下。同一份特征表、同一
   seed、同一仓库，`OMP_NUM_THREADS=1` 得 C0 seed0 MAE
   `0.0015997225046157837`，默认线程数得 `0.0015666428208351135`，差 **2.1%**。
   线程数改的是 BLAS 的浮点累加顺序，300 个 epoch 会把它放大。
   默认线程数还有个更糟的后果：结果随机器核数变化，换台机器就复现不了。
   所以重跑统一钉在 `--threads 1`，并在产物里记 `torch_num_threads`。
2. **torch 版本**。同一份特征表、同一 seed，torch `2.10.0+cpu` 得
   `0.0015666428208351135`，torch `2.14.1+cpu` 得 `0.0015434211492538453`。
   用 2.10.0 重跑能**逐位复现**本目录的值，用 2.14.1 不能——所以这不是
   随机性，是换了 BLAS 内核。`scripts/rerun_all.py` 会核对解释器的 torch
   版本与记录是否一致，不一致直接拒绝。

`scripts/rerun_all.py` 的预检把这两条都做成了硬闸门。绕过它们需要显式传
`--allow-torch-mismatch`，而线程数不一致没有绕过开关——那是纯粹的配置错误。
